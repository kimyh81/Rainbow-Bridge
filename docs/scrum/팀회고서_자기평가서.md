## 5. 팀 회고서

### 5-1. 협업 잘된 점

**① Git 브랜치 전략 및 문서화**  
- 인당 1브랜치 전략을 처음부터 끝까지 유지했습니다. 총 PR **365건**, 커밋 **1,439건** 이상이 쌓였고, 각 PR에 목적과 변경 내용을 기록하는 습관이 자리잡혔습니다.  
- `CLAUDE.md`, `CONTRIBUTING.md`, `GIT_GUIDE.md` 등 팀 공용 가이드 문서를 초기에 작성해 Git이 처음인 팀원도 흐름을 따라올 수 있었습니다.

**② 역할 분담과 병렬 작업**  
- 백엔드(모세종·김윤한) / AI-LLM(반소람·정환주) / 프론트(민경이) / 멀티모달(장민수) 로 역할이 명확히 나뉘어 병렬로 진행됐습니다.  
- 각자의 영역을 건드릴 때 먼저 알리는 문화가 유지되어 충돌 없이 머지가 가능했습니다.

**③ 빠른 문제 해결 사이클**  
- NCP 서버 재시작으로 DB 초기화 → 시드 스크립트 재실행, voiced_url 소실 → DB 직접 복구, Cloudflare Tunnel URL 변경 → `.env` 즉시 갱신 등 문제 발생 후 당일 해결 사이클이 정착됐습니다.  
- 스크럼 회의록에 이슈·원인·조치를 빠짐없이 기록해 팀원 전원이 상황을 공유했습니다.

**④ 강사 피드백 즉각 수용**  
- PERSO 립싱크 드랍 결정(2026-06-06), 1인칭 화법 허용 조건 강화(2026-06-09), MuseTalk→LivePortrait 파이프라인 제안(2026-06-17) 등 강사 피드백을 24시간 이내에 반영했습니다.

**⑤ 윤리 기준 사전 설계**  
- 추모 표현 허용/금지 가이드(`ETHICS_추모표현_가이드.md`)를 별도로 작성하고, risk_level 2+ 시 1인칭 영상 생성 차단 로직을 코드 수준에서 구현했습니다. 발표 전날까지 위기 안내 번호 1393이 코드에 하드코딩되어 임의 변경되지 않았습니다.

### 5-2. 개선점

**① 인프라 영속성 미비**  
- MongoDB Docker volume이 비영속으로 설정되어 서버 재시작마다 DB가 초기화됐습니다. 초기에 `volumes:` 설정을 확인했다면 반복적인 재시드 작업을 줄일 수 있었습니다.

**② 삼성헬스 캐시 설계 누락**  
- `AsyncStorage`의 `health_latest` 키가 pet별로 분리되지 않아 여러 데모 계정에서 동일한 기기 걸음수가 표시됐습니다. 기능 설계 단계에서 multi-pet 시나리오를 고려했다면 방지할 수 있었습니다.

**③ 데모 계정 세팅 후순위**  
- 데모 계정(demo00~demo05)의 시나리오 데이터가 발표 전날 완성됐습니다. 1~2일 일찍 세팅했다면 E2E 검증 시간을 더 확보할 수 있었습니다.

**④ CI 체크 생략 관행**  
- 발표 직전 일정 압박으로 `--admin` 플래그를 사용한 강제 머지가 다수 발생했습니다. `ruff·black·pytest` 사전 검사가 습관화됐다면 CI 실패 후 핫픽스 PR을 줄일 수 있었습니다.

**⑤ TTS 한도 관리**  
- WaveSpeedAI·Gemini TTS 무료 한도를 미리 파악하지 않아 데모 중 한도 초과 위험이 있었습니다. 사전 생성 wav 파일을 더 일찍 고정했다면 안정성이 높아졌을 것입니다.

### 잘한 점

- **문서를 코드처럼 관리**했습니다. CLAUDE.md에 팀 공용 규칙을 정리해 Git이 처음인 팀원도 일관된 브랜치·커밋 습관을 유지할 수 있었습니다.
- **문제가 생기면 당일 해결**하는 원칙을 지켰습니다. 서버 재시작·voiced_url 소실·CI 실패 등 크고 작은 이슈를 발표 전날까지 모두 처리했습니다.
- **윤리 기준을 기술로 구현**했습니다. risk_level 게이트, 1인칭 노출 조건, 1393 하드코딩이 코드 수준에서 보장됩니다.

### 아쉬운 점

- MongoDB volume 설정 같은 **인프라 기초**를 프로젝트 초반에 점검하지 못해 반복적인 재시드 작업이 발생했습니다.
- 발표 직전까지 `--admin` 강제 머지를 사용하며 **CI 신뢰도**를 낮췄습니다. 평소에 `ruff·black·pytest`를 push 전에 돌리는 습관을 더 철저히 지켰어야 했습니다.
- 팀원들의 PR을 더 꼼꼼히 리뷰하지 못하고 일정 압박으로 빠르게 머지한 경우가 있었습니다.

### 배운 점

- 서비스 기획(B2B2C 방향 전환, 윤리 경계 설계)부터 인프라 운영까지 처음으로 전체 스택을 경험했습니다.
- AI 기능(LLM·TTS·LivePortrait)을 백엔드 API로 묶는 **오케스트레이션 설계**의 복잡함을 체감했고, 폴백 전략의 중요성을 배웠습니다.
- Git 협업 문화가 팀 생산성에 얼마나 큰 영향을 미치는지 직접 확인했습니다.
