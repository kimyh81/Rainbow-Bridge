- 자동화(watchdog/keeper/GPU 자가복구)가 드문 간헐 hang·URL변경·크래시를 무인 수습 중. 사람이 손댈 일은 평소 없음.

## 1. 시스템 구조

```
[앱] → [NCP 백엔드(GPU 없음)] → [cloudflared 터널] → [GPU 서버 8003] → [Qwen3-TTS bf16 ~4.6GB]
                  │ 실패/지연 시
                  └→ [구글 TTS 폴백] (항상 작동)
```
- 백엔드는 GPU가 없어 직접 합성 불가 → GPU 서버를 HTTP로 호출.
- 긴 메시지는 **비동기 폴링**: `POST /synthesize/async`(job_id) → `GET /synthesize/status/{id}` → `GET /synthesize/result/{id}`. 동기 `/synthesize`는 하위호환 유지.
- 라우터는 루트(`/...`)와 `/tts/...` 양쪽 마운트 → 백엔드 URL이 직결이든 프록시든 안 깨짐.

## 2. 에러 모드 사전 (증상 → 원인 → 해결)

| 증상 | 진짜 원인 | 해결 | 위치 |
|------|-----------|------|------|
| `status=None` / `Name or service not known` | 백엔드가 **죽은(옛) 터널 URL** 조회(DNS 실패) | watchdog URL 자동등록(Redis TTL 300s)·`.env` 폴백 | [URL handoff](TTS_URL_AUTO_HANDOFF.md) |
| `404` | 터널 8003 직결 후 백엔드 `/tts` 경로가 서버에 없음 | server.py가 `/`·`/tts` 양쪽 받게 함 | server.py 라우터 이중마운트 |
| 목소리 다 똑같음 | 백엔드 키(`voice`)와 서버 키(`tone`) 불일치 | `AliasChoices("tone","voice")`로 둘 다 받음 | server.py `SynthesizeRequest` |
| `500` (합성) | `_OUTPUT_DIR` **상대경로** → 자동기동 CWD(시스템폴더)서 `WinError5` | 기본값을 모듈 옆 **절대경로**로 | qwen3_synthesize.py `_OUTPUT_DIR` |
| `503` (합성) | VRAM 고갈/혼잡 → `_inflight≥4` 또는 `_gpu_sem` 타임아웃 | 대기큐·degraded 차단(죽음의 소용돌이 방지) | server.py |
| **`502`** (앱/백엔드) | **GPU 재시작 ~20초간 origin(8003) 다운** → cloudflared 502 | 재시작 끝나면 자동 해소(그 사이 구글 폴백). **hang을 줄여야 502도 줄어듦** | (불가피한 증상) |
| `502` (watchdog 로그) | watchdog→NCP 백엔드 등록 POST 중 백엔드가 그 순간 502 | 다음 루프 30초 뒤 재등록 성공 | (TTS 무관) |
| **600자 메시지가 폴백됨 / `degraded:true`** | **`_SYNTH_TIMEOUT=150s` < 합성시간(600자=~200s)** → GPU 상태 무관 무조건 타임아웃 → degraded | **타임아웃 150→300s**(§4). 드문 진짜 hang은 자동재시작+폴백 | §4 |

## 3. hang 해결 역사 (1차~5차) — 무엇이 잡혔고 무엇이 남았나

| 차수 | 발견 | 조치 | 결과 |
|------|------|------|------|
| 1차 | 특정 문장서 codec EOS 미방출 → 8192토큰 폭주(수백초) | `max_new_tokens` 상한(현 3072, 청크경로 1024) | 폭주성 hang 차단 ✅ |
| — | 긴 메시지 70초 > 백엔드 60초 타임아웃 → `context canceled` | **비동기 잡 전환**(async/status/result) | 길이·터널 무관 ✅ |
| 2차 | `WinError5` (출력경로 상대경로 + 자동기동 CWD) | `_OUTPUT_DIR` 절대경로 | 500 해소 ✅ |
| 3차 | VRAM 746MB 고갈 → job hang → 세마포어·VRAM 영구점유 | `_SYNTH_TIMEOUT=150s` + `_degraded` 플래그(2차생성 차단) | 소용돌이 차단 ✅ |
| 4차 | VRAM 단편화 | `PYTORCH_CUDA_ALLOC_CONF=expandable_segments` + 매 합성후 `empty_cache()` + **재부팅(7GB 회수)** | 깨끗한 GPU선 134자 46초 done ✅ |
| **5차** | 재부팅 후 VRAM 다시 2.2GB로 축소(원격+앱) → hang 재발 | 문장 청크 합성 시도(180자 단위) → 측정 후 **되돌림** | **절반 성공이라 revert**(§4) |
| **★6차** | **진짜 원인**: hang 아니라 `_SYNTH_TIMEOUT=150s` < 합성시간(600자=200s). 1~5차는 증상만 봄(134자=46s만 통과시켜 "깨끗하면 됨" 착각) | 타임아웃 150→**300s** + 깨끗 GPU 직접측정으로 입증 | **해결**: 586자 실서버 async=done 200s ✅ (§4) |

## 4. ★최종 결론 — 합성 타임아웃 < 합성시간 (2026-06-14 6차, 직접 측정으로 확정)

> **5차까지 "환경 벽"으로 오진단했다. 6차에서 정정.** 아래는 그 정정 기록.

### 진짜 원인 (타임아웃 < 합성시간)
- 합성시간 ≈ **0.35초/자**(RTF 2.1, flash-attn 미설치). memorial 프롬프트는 **600자**를 강제 → 합성 ~200초.
- server.py `_SYNTH_TIMEOUT`은 **150초**였음 → **420자 넘는 메시지는 GPU 상태와 무관하게 무조건 잘림** → `_degraded`→전체 폴백.
- **깨끗한 GPU 직접 측정**(원격 끊고 8003 서버 내려 VRAM 6.5GB 확보, `synthesize()` 직접 호출·타임아웃 없음):
  - 413자 → **177.8초 완료** (오디오 83초)
  - 586자 → **203.5초 완료** (오디오 94.3초)
  - → **둘 다 hang 아님, 끝까지 정상 합성.** "stall"의 정체 = 합성이 진행 중인데 150초에 잘린 것.

### 수정 + 검증
- `_SYNTH_TIMEOUT` **150 → 300초** (600자 200초 + 여유, 백엔드 폴링 360초 안).
- **실서버 async 검증: 586자 = `done` 200초** ✅ (폴백 아님, qwen3로 끝까지).

### 왜 5차까지 오진단했나 (교훈)
- **134자(46초)만 테스트**해서 통과 → "깨끗한 GPU면 된다"고 착각. 실서비스 600자(200초)가 150초 타임아웃을 넘는 걸 못 봄.
- **GPU util 15~19% 낮음을 "경합 증거"로 오독.** autoregressive 디코딩은 배치1이라 원래 util 낮음(메모리 바운드) — 경합이 아니라 토큰을 많이 생성하는 중이었을 뿐.
- 메모리/요약만 보고 추론하고 **실제 코드(`_SYNTH_TIMEOUT` 상수)를 안 읽음.** → 실측 + 코드 정독으로 정정.

### 폐기된 오답 (다 헛다리였음)
- ❌ 청크 합성 · ❌ int8 양자화 · ❌ 재부팅 운영 · ❌ 클라우드 GPU(월 비용) · ❌ "환경 벽이라 코드론 못 푼다"
- 합성은 멀쩡히 작동했다. 타임아웃이 일찍 잘랐을 뿐. **클라우드도 재부팅도 비용도 필요 없었음.**

### 남은 사실
- **환경(원격+앱)은 악화요인은 맞다** — VRAM 고갈 시 진짜 간헐 hang(예: 5차 34자 2분)이 드물게 날 수 있고, 그건 `_degraded`→폴백→자동재시작이 처리. 단 **600자가 막힌 1차 원인은 아님**.
- **UX**: 600자 합성 ~200초(3.3분). 프론트가 폴링 표시해야 함(윤한/민경이 범위).
- **속도(선택)**: flash-attn 설치 시 RTF 개선 가능(별도 작업).

## 6. 진단 런북 (TTS 깨졌을 때 순서대로)

```powershell
# 1) GPU 서버 살아있나 + degraded 여부
Invoke-RestMethod http://127.0.0.1:8003/health
#  model_ready:true,degraded:false = 정상 / degraded:true = hang 감지(자동재시작 대기)

# 2) 현재 터널 URL (cloudflared metrics 포트 → /quicktunnel)
$mp = (Get-NetTCPConnection -OwningProcess (Get-Process cloudflared).Id -State Listen).LocalPort
Invoke-RestMethod "http://127.0.0.1:$mp/quicktunnel"

# 3) 터널 경유 health (외부 접근 확인)
Invoke-WebRequest https://<url>.trycloudflare.com/tts/health

# 4) VRAM 여유 (2GB 미만이면 hang 위험)
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.free --format=csv,noheader

# 5) watchdog 동작 로그 (어느 단계서 막혔나: [GPU]/[터널]/[등록])
Get-Content C:\Rainbow_Bridge\logs\tts_url_watchdog.log -Tail 20
```

**GPU 서버 수동 재시작** (degraded 클리어·멈춘 스레드 제거·새 코드 로드):
```powershell
$pid = (Get-NetTCPConnection -State Listen -LocalPort 8003).OwningProcess
Stop-Process -Id $pid -Force
pwsh -NoProfile -File C:\Rainbow_Bridge\gpu_server_start.ps1   # 8080/cloudflared 이미 떠있으면 스킵 → URL 유지
```
> ⚠️ 서버 stdout은 `--no-capture-output`로 버려짐 → `print` 안 남음. 합성 에러는 **async status의 `error`** 또는 `logs\gpu_tts_stderr.log`로 확인. 청크 타이밍은 `tts_chunk_timing.log`.
