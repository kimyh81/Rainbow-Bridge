# 회복점수 × 삼성헬스 — 설계·흐름 노트

> 작성 정환주 · `ai/evaluation/` · 최종 갱신 2026-06-13
> **목적:** 삼성헬스의 **객관 수면·활동 데이터**를 회복점수에 반영(+주관 감정과 교차검증).
> 코드 세부는 각 파일(`health_signal.py`·`health_adapter.py`·`health_export_adapter.py`)에 있고,

## 0. 결정 요약 (확정 사항)

| 항목 | 확정 | 이유 |
|------|------|------|
| 회복점수 핵심 가중치 | 감정 40 · 미션 35 · 꾸준 25 | 결정문서 §1 정본 |

## 1. 왜

지금 회복점수는 **주관 감정 체크인(1~10)** 위주 → 매번 입력해야 하고 주관적.
삼성헬스에 이미 쌓이는 수면·활동을 더하면 ① 객관성 보강 ② "센서는 수면이 나쁜데 본인은
괜찮다더라" 같은 **숨은 위험** 포착.

---

## 2. 무슨 데이터를 가져와서 어떻게 쓰나 ★

> 핵심. "연결"이 목적이 아니라 **무슨 항목을 어디에 쓰는지**가 설계입니다.

| 데이터 | 어디서 | 회복점수 | 그 외 활용 |
|--------|--------|----------|-----------|
| **걸음 수** | 삼성헬스 `Steps` (하루 합산) | ✅ **활동 +10점** (8000걸음=만점) | 활동 미션과 연동(예정) |
| **수면 시간** | 삼성헬스 `SleepSession` (취침~기상) | ❌ **제외** | ① 교차검증(감정과 대조) ② **컨디션 추정**(`condition_signal`) ③ 리포트 "참고" 표시 |

**왜 걸음만 점수, 수면은 빼나?**
- 걸음 = 회복기 **활동성**의 직접 신호 → 점수 add-on 적합.
- 수면 = 애도기엔 못 자는 게 정상 → 점수로 깎지 않고, **객관 수면 vs 주관 기분의 어긋남**을
  잡는 교차검증·컨디션 추정 재료로만.

> ⚠️ **수면은 "두 트랙"이 따로 있습니다(이름만 같고 데이터·담당·코드가 다름):**
> | 트랙 | 데이터 | 용도 | 담당 |
> |------|--------|------|------|
> | **객관 수면시간** (본 문서) | 삼성헬스 `sleep_hours` | 교차검증 · 컨디션 추정 · 표시 | **정환주** |
> | **주관 수면질 5단계** | `sleep_quality`(1~5 체크인) | **미션 난이도 보조** | 반소람(modifier)·모세종(스키마)·민경이(UI) |
>
> 둘 다 **회복점수 산식에선 제외**(이건 일치). 코드 경로도 완전 별개라 서로 안 닿음.

> 주의: 데이터는 **하루치만** 가져와 넘긴다(여러 날 합치면 과대평가).

## 3. 회복점수 산식

| 항목 | 가중치 | 반영 |
|------|--------|------|
| 감정(주관) | 40 | ✅ 항상 |
| 미션 누적 | 35 | ✅ 항상 (천장 35) |
| 꾸준함(최근14일 체크인) | 25 | ✅ 항상 |
| 활동(걸음) | 10 | ⭕ 들어올 때만 |

각 항을 0~1 비율로 환산 → 가중합 → 들어온 항목의 가중치 합으로 나눠 0~100.
**예:** 감정 8 · 미션 10개 · 꾸준 80% · 9000걸음 → **65점** (활동 데이터 없으면 61점 →
걸음이 들어오면 올려주는 방향, 깎지 않음).

## 4. 교차검증 — 수면(객관) vs 감정(주관)

수면은 점수엔 없지만 여기서 살아있음. **점수 안 깎고 플래그 + 따뜻한 문장**만.

| 수면 | 감정 | 의미 |
|------|------|------|
| 나쁨 | 좋음 | `mismatch_high_risk` — "못 잤다는데 괜찮다고 함" = **숨은 위험** |
| 좋음 | 나쁨 | `mismatch` — 잘 잤지만 마음이 무거움 |
| 나쁨 | 나쁨 | `agree_low` — 몸도 마음도 지침 |
| 그 외 | | `agree_ok` |

보호자에게 보이는 문장은 비낙인·위로 톤, 임상 해석은 내부 코드로만. (1393 위기 트랙과 별개)

**컨디션 추정(`condition_signal`):** 위 교차검증 + 수면·감정을 묶어 **오늘 컨디션(양호/주의/보통)
+ 신뢰도**를 낸다. 강사 구상("수면+체크인 → 컨디션 추정")이 바로 이것. **회복점수와 별개 출력**으로
리포트 응답 `recovery_signal.condition` 에 실린다.
- 수면 82 + 기분 좋음 → **양호/높음**
- 수면 나쁨 + 기분 좋음 → **주의/낮음** (센서는 나쁜데 괜찮다 = 숨은 위험)
- **기분 나쁜 날은 수면 유무·질과 무관하게 '주의'** (사별 케어 — 안전쪽으로 기울임)

## 5. 전체 흐름

```
삼성헬스 앱 ──(설정: Health Connect 동기화 ON)──▶ Health Connect
                                                       │
 [실시간]  RN 앱(개발빌드) ─걸음·수면 읽기─────────────┘
       └─▶ 백엔드(POST /health/sync) ─▶ health_logs 적재 ─▶ GET /report (회복점수+교차검증+컨디션)

 [백업]   삼성헬스 → 개인 데이터 내보내기(zip) ─▶ load_samsung_export ─▶ health_logs ─▶ (같은 회복점수)
          ※ 폰·개발빌드 불필요 — 발표용 실데이터 경로 (적재 스크립트로 health_logs 에 직접 넣음)
```

점수 로직은 **순수 함수**(DB·네트워크 없음)라 더미로 이미 테스트됨(`ai/evaluation` 79개 +
`backend` 리포트 8개 통과). 실연동은 "같은 입력에 실데이터를 꽂는" 일.

## 6. 지금 어디까지 / 남은 일

**된 것:** 점수 엔진·어댑터·교차검증·**컨디션 추정**(`condition_signal`)·테스트·발표용 백업 파서
+ **백엔드 배선**(`get_report`가 `health_logs` 읽어 점수 반영 + `recovery_signal.condition` 노출,
`POST /health/sync` 입구) = 완료(fake-DB 테스트 검증).
**남은 것:** `health_logs` 에 실데이터가 **NCP(발표 백엔드) mongo** 에 들어가야 `GET /report` 에 보임 —
export 적재(A, 스크립트 완성) 또는 RN 동기화(C, 민경이). 적재 스크립트는 완성됐고, **어느 mongo 에 넣을지(NCP)** 만
실행 시점에 정하면 됨. (배선 자체는 양쪽 공통 = keystone)

| 버킷 | 내용 | 담당 | 상태 |
|------|------|------|------|
| **A** | 삼성헬스 export 파서 **+ `health_logs` 적재 스크립트** (폰 없이 발표 실데이터) | **정환주 단독** | ✅ **완료·검증** · 실 export(2026-06-12)로 컬럼 확정, `load_samsung_export.py` 로 실데이터 추출·적재 동작 |
| **B** | 백엔드 배선 (`POST /health/sync` + `get_report`가 `health_logs` 읽어 점수 반영) | **정환주**¹ | ✅ 배선 완료 · fake-DB 테스트로 "걸음→blend 점수" 검증³ |
| **C** | RN 앱에서 삼성헬스 읽기 + 개발빌드 → `POST /health/sync` 호출 | 민경이 협의² | ⬜ (계약은 §7) |

### 6-A. export 실데이터 적재 — `load_samsung_export.py`

폰/개발빌드 없이 삼성헬스 **개인 데이터 내보내기(zip)** 로 발표용 실데이터를 `health_logs` 에 넣는다.
파싱 결과를 `POST /health/sync` 와 **같은 문서 모양**(`{pet_id, date, steps, sleep_hours, synced_at}`,
+식별용 `source:"samsung_export"`)으로 upsert → `GET /report` 가 회복점수에 반영.

```bash
# 1) 무엇이 들어갈지 확인만 (DB 안 건드림 — 기본값)
python -m ai.evaluation.load_samsung_export <samsunghealth_*.zip> --pet-id <PET_ID>

# 2) 실제 적재 — 발표 리포트에 보이려면 그 백엔드(NCP)의 mongo 여야 함
python -m ai.evaluation.load_samsung_export <zip> --pet-id <ID> \
    --write --mongo-uri "mongodb://<NCP_HOST>:27017" --db rainbow_bridge
```

- **기본은 출력만**(안전). `--write` 줄 때만 적재하고, 대상 URI 를 화면에 크게 찍는다.
- `GET /report` 는 `health_logs` 에서 **pet_id 의 가장 최근 date 1건**만 읽음 → 발표용 문서가 최신이어야 보임.
  필요하면 `--date YYYY-MM-DD` 로 강제(같은 날짜 실 sync 문서 있으면 덮어쓰니 경고 출력).
- ⚠️ **로컬 27017 에 넣으면 NCP 리포트엔 안 나옴.** 발표 대상 mongo 에 넣을 것.
- ⚠️ 실 export 는 걸음만 최근까지, 수면은 거의 없음 → 최근 날짜는 보통 **걸음만(`sleep_hours=None`)**.
  수면-감정 교차검증 데모는 실데이터가 아니라 시뮬레이션(`demo_health_report.py`)으로 보여줄 것.

¹ 2026-06-09 역할 재분담으로 백엔드 기능개발도 환주 영역(모세종 합의 대기 없이). 단 `backend/`
  푸시 전 `ruff·black·pytest`, main/dev 직접 push·커밋·PR은 규칙대로(시킬 때만).
² 삼성헬스는 Expo Go(공용 앱)로 못 읽음 → 개발빌드 필요. 공용 앱에 직접 넣으면 팀 전원
  Expo Go 깨지므로 **격리 브랜치 + 민경이 협의 + 별도 PR.**
³ **fake-DB 단위테스트로 검증(라이브 요청 아님).** `backend/tests/test_report_service.py` 의
  `test_get_report_health_logs_reach_recovery_score` — 걸음 9000이 들어오면 회복점수 산식이
  base→`blend` 로 전환되는 것까지 확인. (로컬은 starlette 버전 충돌로 앱 전체 import만 막힘 —
  CI 정상 예상. `backend/` 푸시 전 `ruff·black·pytest` 통과.)

**순서:** A(거의 완료) → B(환주 직접) → C(민경이). **A만으로 발표 실데이터 시연 가능.**

## 7. 팀 핸드오프 — 누가 무엇을 ★

> "삼성헬스 부분 어떻게 해야 하나" 한눈에. 정환주(A·B)는 끝났고, **남은 실작업은 민경이(C)** 입니다.

### 7-1. 민경이 (프론트 / RN) — 버킷 C, 유일한 미착수

목표: RN 앱에서 삼성헬스(→Health Connect) 걸음·수면을 읽어 **`POST /api/v1/health/sync`** 로 보내기.
백엔드·점수·적재는 다 돼 있으니, **읽어서 쏘기**만 하면 `GET /report` 에 실데이터 회복점수가 나옵니다.

**왜 그냥은 안 되나 (먼저 이해):**
- 삼성헬스는 **Expo Go 로 못 읽습니다**(네이티브 모듈). → **개발빌드(EAS)** 필요.
- 삼성헬스 ≠ Health Connect. 사용자가 [삼성헬스 설정 → Health Connect **동기화 ON**] 켜야 데이터가 넘어옴.
- 공용 Expo Go 워크플로를 깨지 않으려면 **격리 브랜치 + 별도 PR**(공용 앱에 직접 넣으면 팀 전원 Expo Go 깨짐).

**할 일 (순서):**
1. `react-native-health-connect`(검토 시점 `@3.5.3`) 설치. `app.json` plugins 에 등록.
2. `eas.json` 추가 → **안드로이드 개발빌드** 1개 만들기(Expo Go 아님).
3. Health Connect 권한 요청 → `readRecords('Steps', ...)`, `readRecords('SleepSession', ...)`.
4. 읽은 **원본 JSON 을 그대로** 백엔드로 전송(파싱은 백엔드 어댑터가 함):

```jsonc
// POST /api/v1/health/sync   (Authorization: Bearer <토큰> 필요)
{
  "pet_id": "<반려동물 id>",
  "steps_result": { "records": [ { "count": 5000, "startTime": "...", "endTime": "..." } ] },
  "sleep_result": { "records": [ { "startTime": "...", "endTime": "...", "stages": [] } ] }
}
// 응답: { "ok": true, "date": "YYYY-MM-DD", "steps": 5000, "sleep_hours": 7.5 }
```

- `steps_result`/`sleep_result` = Health Connect `readRecords` **응답 그대로** 넣으면 됨(키 가공 X).
- 둘 중 하나만 보내도 됨(없으면 생략). 백엔드가 `{steps, sleep_hours}` 로 변환해 `health_logs` 에 날짜별 upsert.
- ⚠️ 삼성헬스 모듈은 **격리 브랜치에서**. 민경이 혼자 막히면 정환주가 RN 코드·개발빌드 가이드 작성 보조 가능(설치·권한 "허용" 탭만 사람 손 필요).

### 7-2. 반소람 (AI / 미션·메시지) — 선택

객관 데이터(`steps`/`sleep_hours`/`cross_check`/`condition`)를 미션·메시지에 쓰고 싶으면
출력 스키마·사용법은 **[HANDOFF_헬스데이터_스키마_반소람.md](HANDOFF_헬스데이터_스키마_반소람.md)** 참고(중복 생략).
주관 수면질 5단계(`sleep_quality`)는 **다른 트랙** — §2 경고 박스 참고.

### 7-3. 정환주 (본인) — A·B 완료, 발표 직전

- 발표용 실데이터: §6-A `load_samsung_export.py` 로 **NCP mongo** 에 `--write`(로컬 27017 아님).
- 코드·배선·테스트 완료. `backend/` 푸시 전 `ruff·black·pytest`, **삼성헬스 PR 은 APK 개발빌드 후**(세종 지시).

## 8. 용어 (짧게)

- **Health Connect** — 안드로이드 표준 건강데이터 허브. 삼성헬스와 **별개** → 삼성헬스 설정에서
  동기화 ON 해야 데이터가 넘어옴.
- **개발빌드** — Expo Go로 못 쓰는 네이티브 모듈을 넣은 전용 앱. Health Connect 읽으려면 필수.
- **교차검증(cross_check)** — 객관 수면 vs 주관 감정 어긋남 탐지(점수 안 깎고 플래그만).
- **재정규화(옵션 A)** — 빠진 데이터를 분모서 빼서 점수 안 깎이게 하는 방식.
- **export 백업 경로** — 폰 연동 전, 삼성헬스 데이터 내보내기 파일로 실데이터 시연하는 길.
