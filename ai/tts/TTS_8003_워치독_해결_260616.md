# 🌈 Rainbow Bridge TTS — 8003 워치독 사태 해결 (2026.06.16)

> 06-14 핸드오프(`TTS_해결과정_260614.md`)의 후속. "watchdog 종료"로 합의했던 게
> **자동시작(Startup)으로 부활**해 재발한 건을 추적·영구 차단한 기록.

---

## 📋 증상

- GPU 전용 메모리(VRAM)가 8GB 거의 풀(7.3~7.6GB)로 계속 차오름 → qwen3 합성 정체/OOM 위험
- 어제는 5~6GB로 안정적이었음
- **8003 포트를 `taskkill`로 죽여도 잠시 후 다른 PID로 부활** (두더지 잡기)
- 손으로 등록한 8002 URL이 자꾸 8003으로 덮이는 느낌

---

## 🔍 근본 원인

`tts_url_watchdog.vbs` (Startup 폴더, 06-14 01:17 생성)
→ 로그인마다 **keeper + watchdog**를 숨김 실행:

```
Startup\tts_url_watchdog.vbs   (자동시작 진입점)
  └ tts_watchdog_keeper.ps1     (keeper = supervisor, 워치독 죽으면 재기동)
      └ tts_url_watchdog.ps1     (watchdog)
          ├ conda run python server.py  (PORT=8003 → 8003 TTS 서버 별도 가동)
          ├ cloudflared --url localhost:8003  (8003 터널 별도 가동)
          └ 120초마다 백엔드에 8003 URL 자동 재등록
```

문제 3가지:
1. **VRAM 이중 점유** — 8002(팀 합의 서버) + 8003(워치독 서버), qwen3 모델 2개가 8GB GPU에 동시 적재 → 고갈
2. **백엔드 URL 덮어쓰기** — 워치독이 2분마다 8003 URL을 register-url에 POST → 수동 등록한 8002가 계속 8003으로 갈아치워짐
3. **죽여도 부활** — keeper가 watchdog 재기동, .vbs가 부팅마다 keeper 재기동

> 참고: 06-14 핸드오프 #8 "watchdog이 30초마다 이전 URL로 덮어씀 / 8003→8002 잘못 연결"이
> 바로 이 구조였음. 그때 프로세스만 죽이고 .vbs 자동시작은 안 지워서 재발.

## 🛠️ 진단 경로 (재현용)

```powershell
# 1) qwen3 프로세스 개수 — 2개면 중복
nvidia-smi

# 2) 의심 포트의 점유 PID
netstat -ano | findstr 8003

# 3) 그 PID가 어떻게 떴는지 부모 체인 역추적
Get-CimInstance Win32_Process -Filter "ProcessId=<PID>" | Select ProcessId,ParentProcessId,CommandLine | Format-List
# → 부모 PID로 반복하면 최상위(keeper / .vbs)까지 도달

# 4) 워치독/keeper pwsh 존재 확인
Get-CimInstance Win32_Process -Filter "Name='pwsh.exe'" | ? {$_.CommandLine -like '*watchdog*' -or $_.CommandLine -like '*keeper*'} | Select ProcessId,CommandLine

# 5) 자동시작 진입점 확인
Get-ScheduledTask | ? { ($_.Actions | % Arguments) -like '*keeper*' }
Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"
```

## ✅ 해결 순서 (부모 → 자식 순으로 죽여야 부활 안 함)

```powershell
# 1) keeper 종료 (워치독 재기동 차단)
Stop-Process -Id <keeper_pid> -Force

# 2) watchdog 종료
Stop-Process -Id <watchdog_pid> -Force

# 3) 8003 서버 종료 (VRAM 회수)
Get-NetTCPConnection -LocalPort 8003 -State Listen -EA SilentlyContinue | % { taskkill /PID $_.OwningProcess /F }

# 4) 8003 cloudflared 터널 종료
Get-CimInstance Win32_Process -Filter "Name='cloudflared.exe'" | ? {$_.CommandLine -like '*localhost:8003*'} | % { Stop-Process -Id $_.ProcessId -Force }

# 5) 자동시작 영구 차단 (삭제 대신 비활성화 — 되돌리기 쉬움)
Rename-Item "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\tts_url_watchdog.vbs" "tts_url_watchdog.vbs.disabled"
```

## 🔑 백엔드 URL 등록 규칙

- 백엔드 저장소: Redis `tts:server_url`
- **직접 set 권장** (TTL 없이 영구). register-url 엔드포인트는 TTL 300s라 워치독 없이는 5분 후 만료 위험.
- **주소는 base만** — `/tts` 붙이지 않음
  - 서버 합성 경로 = `host/tts/synthesize/...`
  - 백엔드가 등록 URL 뒤에 `/tts/synthesize`를 자동으로 붙임
  - 워치독이 `/tts` 붙여 등록 → `host/tts/tts/synthesize` 중복 → 404 (06-14 버그 원인)

윤한님 요청 문구 예시:
> Redis `tts:server_url` = `https://<현재-quick-tunnel>.trycloudflare.com` 직접 set (TTL 없이, `/tts` 미포함)

수동 POST 방식(TTL 주의):
```powershell
Invoke-RestMethod -Uri https://rainbow-bridge.duckdns.org/api/v1/tts/register-url -Method Post `
  -Headers @{"X-TTS-Secret"="[TTS_SECRET — 별도 보관]"} -ContentType "application/json" `
  -Body (@{url="https://<현재-quick-tunnel>.trycloudflare.com"} | ConvertTo-Json)
```
